# Документация проекта: "Norbit.ID" — единая система аутентификации и сессий

## 📖 Общее описание

**Norbit.ID** — это микросервисная система аутентификации, аналогичная Яндекс.ID или Google Sign-In, которая предоставляет единый аккаунт для доступа к различным сервисам экосистемы. Система централизует управление пользователями, сессиями и авторизацией, позволяя другим сервисам сосредоточиться на своей бизнес-логике.

**Ключевые возможности:**
- 🔐 Единая точка входа для всех сервисов
- 🛡️ Многоуровневая система безопасности
- 📱 Поддержка веб и мобильных клиентов
- 🔄 Автоматическое управление сессиями
- 🚀 Готовность к масштабированию

## 🏗️ Архитектура и решения

### Микросервисный подход
Система построена по принципу микросервисной архитектуры с четким разделением ответственности:
- **Auth Service** — ядро системы, управляет пользователями и сессиями
- **Nginx** — единый entry point, прокси и балансировщик
- **PostgreSQL** — основное хранилище данных
- **Redis** — кэш, сессии, очереди и временные данные
- **Notification Service** — отправка email и уведомлений

### Технологический стек
- **Backend:** Python 3.14 + Flask (легковесный, гибкий)
- **База данных:** PostgreSQL (надежность, транзакции)
- **Кэш и сессии:** Redis (высокая производительность)
- **Контейнеризация:** Docker + Docker Compose
- **Проксирование:** Nginx (статический контент, балансировка)
- **Аутентификация:** JWT + bcrypt (современные стандарты)

## 🛡️ Система безопасности

### Многоуровневая защита
1. **Защита данных пользователей**
   - Пароли хешируются с помощью bcrypt с автоматической солью
   - Все токены хранятся в хешированном виде
   - Обязательное использование HTTPS в продакшене

2. **Защита сессий**
   - Сессионные куки с флагами HttpOnly, Secure, SameSite
   - JWT токены с коротким сроком жизни (15 минут)
   - Регулярная ротация сессий и токенов

3. **Защита от атак**
   - **Brute Force:** Rate limiting на все эндпоинты
   - **CSRF:** Токены для всех state-changing операций
   - **XSS:** HttpOnly куки, экранирование данных
   - **Session Hijacking:** Хеширование сессий в БД

4. **Внутренняя безопасность**
   - Двухуровневая аутентификация для микросервисов
   - Изоляция данных между сервисами
   - Подробное логирование всех операций

### Rate Limiting
Настроены многоуровневые лимиты:
- **Базовые операции:** 30 запросов в минуту
- **Чувствительные операции:** 5 запросов в минуту
- **Регистрация/логин:** дополнительные ограничения
- **Здоровье сервиса:** либеральные лимиты для мониторинга

## 🔌 Легкое подключение новых сервисов

### 1. Получение токена для сервиса
Новый микросервис получает токен через internal API:
```http
POST /internal/auth/get-service-token
Header: X-API-Key: {ваш_внутренний_ключ}
Body: {"service_name": "your-service"}
```

### 2. Использование токена
Все последующие запросы используют полученный токен:
```http
Header: X-Service-Token: {ваш_сервисный_токен}
```

### 3. Проверка сессий пользователей
Сервисы могут проверять валидность пользовательских сессий:
```python
# Пример middleware для Flask приложения
def require_auth():
    cookie = request.cookies.get('norbit.id')
    session_id, access_token = cookie.split(':')
    
    # Проверка через auth сервис
    result = auth_client.validate_session(session_id, access_token)
    return result.get('valid')
```

### 4. Получение данных пользователя
Сервисы могут получать базовую информацию о пользователе:
```http
POST /internal/auth/get-account-info
Header: X-Service-Token: {токен}
Body: {"session_id": "...", "access_token": "..."}
```

## 📈 Масштабируемость

### Горизонтальное масштабирование
Система спроектирована для легкого масштабирования:

1. **База данных**
   - PostgreSQL с репликацией Master-Slave
   - Возможность шардинга по пользователям

2. **Кэш**
   - Redis кластер для распределенного хранения
   - Разделение по типам данных (сессии, коды, CSRF)

3. **Сервисы**
   - Статeless дизайн auth сервиса
   - Возможность запуска нескольких инстансов
   - Балансировка через Nginx

4. **Уведомления**
   - Асинхронная обработка через Redis Queue
   - Worker процессы для фоновых задач

### Конфигурация масштабирования
Для увеличения производительности:
```yaml
# docker-compose.scale.yml
services:
  auth:
    scale: 3  # Три инстанса auth сервиса
  notifications_worker:
    scale: 5  # Пять воркеров для уведомлений
```

## 🔄 Жизненный цикл сессии

1. **Создание сессии**
   - Пользователь логинится через `/api/auth/login`
   - Система создает сессию в PostgreSQL
   - Генерирует JWT токены (access и refresh)
   - Устанавливает cookie `norbit.id`

2. **Использование сессии**
   - Клиент отправляет cookie с каждым запросом
   - Сервисы проверяют валидность через internal API
   - CSRF токен требуется для изменения данных

3. **Обновление токенов**
   - Access токен живет 15 минут
   - Refresh токен живет 30 дней
   - Автоматическое обновление через `/api/auth/refresh`

4. **Завершение сессии**
   - Ручной выход через `/api/auth/logout`
   - Принудительный выход из всех устройств
   - Автоматический выход при неактивности

## 🗄️ Хранение данных

### PostgreSQL (основная БД)
- **accounts** — пользовательские аккаунты
- **user_sessions** — активные сессии
- **service_tokens** — токены микросервисов

### Redis (временные данные)
- **DB 0:** Rate limiting данные
- **DB 1:** Коды подтверждения
- **DB 2:** CSRF токены
- **DB 3:** Очереди уведомлений

## 🌐 API Структура

### Публичное API (для клиентов)
```
/api/auth/
├── /registration     # Регистрация
├── /login           # Вход в систему
├── /verify          # Подтверждение операций
├── /refresh         # Обновление токенов
├── /logout          # Выход из системы
└── /health          # Проверка здоровья
```

### Внутреннее API (для сервисов)
```
/internal/auth/
├── /get-service-token    # Получение токена сервиса
├── /validate-session     # Проверка сессии
├── /get-account-info     # Информация об аккаунте
├── /get-all-session-info # Все сессии пользователя
└── /logout              # Принудительный выход
```
